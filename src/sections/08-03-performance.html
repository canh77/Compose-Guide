Hiệu suất trong Compose

Compose đủ nhanh cho hầu hết màn hình, nhưng vài thói quen nhỏ có thể làm danh sách bị giật hoặc app khởi động chậm. Phần này giúp bạn đo đúng cách, hiểu vì sao UI chậm và áp dụng các kỹ thuật tối ưu phổ biến.

Định nghĩa

Hiệu suất giao diện là khả năng tạo mỗi khung hình đủ nhanh: khoảng 16 ms với màn hình 60 Hz, và còn ít hơn với màn 90 Hz hay 120 Hz. Khung hình nào trễ hạn sẽ bị bỏ qua, người dùng thấy hiện tượng giật (jank). Mỗi khung hình trong Compose đi qua ba giai đoạn: composition (chạy composable để biết cần hiển thị gì), layout (đo và đặt vị trí) và drawing (vẽ). Xem thêm ở Vòng đời và các giai đoạn.

Tối ưu trong Compose phần lớn xoay quanh hai ý: làm ít việc hơn (tránh recomposition, tức chạy lại composable, khi không cần) và đọc state ở giai đoạn muộn nhất có thể (giá trị chỉ ảnh hưởng tới việc vẽ thì nên đọc ở giai đoạn drawing, khỏi phải chạy lại composition).

Nguyên tắc quan trọng nhất là đo trước khi tối ưu, và đo trên bản release đã bật R8 (công cụ thu gọn và tối ưu mã). Bản debug tắt nhiều tối ưu hóa và mang thêm công cụ hỗ trợ gỡ lỗi nên chậm hơn hẳn; một màn hình giật trên bản debug có thể hoàn toàn mượt trên bản release.

Cách dùng

1. Chuẩn bị bản release để đo

Trong app/build.gradle.kts: bật R8 và tạm ký bằng khóa debug để cài thử trên máy

android {
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
            // Chỉ để thử trên máy của bạn, đừng dùng khi phát hành thật
            signingConfig = signingConfigs.getByName("debug")
        }
    }
}

2. Baseline Profiles

Baseline Profile là danh sách các class và hàm mà app dùng nhiều nhất (lúc khởi động, khi cuộn màn hình chính). Khi app được cài, hệ thống biên dịch sẵn những đoạn mã này thành mã máy, nhờ đó lần chạy đầu khởi động nhanh hơn và ít giật hơn. Các thư viện Compose đã kèm sẵn profile của riêng chúng, nhưng app của bạn nên có profile riêng cho các luồng quan trọng. Cách phổ biến: thêm module Baseline Profile Generator trong Android Studio, module này dùng Macrobenchmark và Baseline Profile Gradle plugin để tự chạy app, ghi lại và đóng gói profile vào bản release.

Ví dụ về ghi ngược: tuyệt đối tránh

@Composable
fun BadCounter() {
    var count by remember { mutableIntStateOf(0) }
    Text("Đã hiển thị $count lần")   // đọc count
    count++                          // ghi ngay sau khi đọc: recompose không bao giờ dừng
}

4. Stability và strong skipping, hiểu đơn giản

Khi composable cha chạy lại, Compose xét từng composable con: nếu mọi tham số giống lần trước thì bỏ qua (skip) con đó. Để biết tham số "giống" hay không, trình biên dịch Compose phân loại kiểu dữ liệu:

  • Ổn định (stable): kiểu nguyên thủy (Int, Boolean…), String, kiểu hàm (lambda), data class chỉ gồm val có kiểu ổn định, class được đánh dấu @Immutable hoặc @Stable.
  • Không ổn định (unstable): class có thuộc tính var thường, các interface List/Set/Map của Kotlin (vì phía sau có thể là danh sách thay đổi được), class từ module không được biên dịch bằng trình biên dịch Compose.

Từ Kotlin 2.0.20, chế độ strong skipping được bật mặc định: composable có tham số không ổn định vẫn có thể được bỏ qua. Tham số ổn định được so sánh bằng equals (giá trị bằng nhau là đủ), còn tham số không ổn định được so sánh bằng tham chiếu (phải đúng cùng một đối tượng). Lambda trong composable cũng được tự động remember. Hệ quả thực tế: nếu mỗi lần recompose bạn tạo một List mới bằng filter, dù nội dung giống hệt thì tham chiếu vẫn khác, nên composable con vẫn phải chạy lại.

Muốn biết hàm nào bỏ qua được và tham số nào không ổn định, bật báo cáo trình biên dịch Compose (compiler reports/metrics) trong block composeCompiler { } của Gradle. Cũng trong block đó, bạn có thể khai báo một file cấu hình ổn định (stability configuration file) để coi các class từ thư viện bên ngoài là ổn định. Với danh sách, có thể dùng ImmutableList của thư viện kotlinx-collections-immutable.

Ví dụ

Ví dụ 1: Lọc danh sách, trước và sau

Trước: lọc và sắp xếp lại toàn bộ danh bạ mỗi lần composable chạy lại

data class Contact(val id: Long, val name: String, val phone: String)

@Composable
fun ContactList(contacts: List<Contact>, query: String) {
    val visible = contacts
        .filter { it.name.contains(query, ignoreCase = true) }
        .sortedBy { it.name }
    LazyColumn {
        items(visible) { contact -> ContactRow(contact) }
    }
}

Sau (cách A): chỉ tính lại khi contacts hoặc query đổi, thêm key cho item

@Composable
fun ContactList(contacts: List<Contact>, query: String) {
    val visible = remember(contacts, query) {
        contacts
            .filter { it.name.contains(query, ignoreCase = true) }
            .sortedBy { it.name }
    }
    LazyColumn {
        items(visible, key = { it.id }) { contact -> ContactRow(contact) }
    }
}

Sau (cách B, tốt hơn cho danh sách lớn): đưa việc lọc vào ViewModel, chạy ngoài luồng chính

class ContactsViewModel(repository: ContactRepository) : ViewModel() {
    private val query = MutableStateFlow("")

    val visibleContacts: StateFlow<List<Contact>> =
        combine(repository.contacts, query) { list, q ->
            list.filter { it.name.contains(q, ignoreCase = true) }.sortedBy { it.name }
        }
            .flowOn(Dispatchers.Default)
            .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

    fun onQueryChange(newQuery: String) {
        query.value = newQuery
    }
}

@Composable
fun ContactsRoute(viewModel: ContactsViewModel) {
    val contacts by viewModel.visibleContacts.collectAsStateWithLifecycle()
    LazyColumn {
        items(contacts, key = { it.id }) { contact -> ContactRow(contact) }
    }
}

Kết quả: Giao diện không đổi, nhưng khi màn hình recompose vì lý do khác (vd mở menu), danh bạ không bị lọc lại. Ở cách B, thao tác nặng chạy trên Dispatchers.Default nên ô tìm kiếm vẫn gõ mượt với hàng nghìn liên hệ. (repository.contacts là một Flow<List<Contact>>; xem ViewModel.)

Ví dụ 2: Nút "Lên đầu" với derivedStateOf

@Composable
fun ArticleFeed(titles: List<String>) {
    val listState = rememberLazyListState()
    val scope = rememberCoroutineScope()

    // Sai: val showButton = listState.firstVisibleItemIndex > 3
    // làm ArticleFeed chạy lại mỗi khi cuộn qua một item.
    val showButton by remember {
        derivedStateOf { listState.firstVisibleItemIndex > 3 }
    }

    Box(Modifier.fillMaxSize()) {
        LazyColumn(state = listState) {
            items(titles) { title ->
                Text(title, Modifier.fillMaxWidth().padding(16.dp))
            }
        }
        AnimatedVisibility(
            visible = showButton,
            modifier = Modifier.align(Alignment.BottomEnd).padding(16.dp)
        ) {
            ExtendedFloatingActionButton(
                onClick = { scope.launch { listState.animateScrollToItem(0) } }
            ) {
                Text("Lên đầu")
            }
        }
    }
}

Kết quả: Khi cuộn qua item thứ 4, nút "Lên đầu" trượt hiện ra ở góc dưới phải; bấm vào thì danh sách cuộn mượt về đầu và nút ẩn đi. Trong Layout Inspector, ArticleFeed chỉ recompose khi nút đổi trạng thái hiện/ẩn, không phải với từng item cuộn qua.

Ví dụ 3: Màu nền nhấp nháy, vẽ bằng drawBehind

@Composable
fun LiveBadge(text: String) {
    val transition = rememberInfiniteTransition(label = "nhap_nhay")
    val bgColor by transition.animateColor(
        initialValue = Color(0xFFD32F2F),
        targetValue = Color(0xFFFF8A80),
        animationSpec = infiniteRepeatable(tween(800), RepeatMode.Reverse),
        label = "mau_nen"
    )

    // Trước: Modifier.background(bgColor, RoundedCornerShape(8.dp))
    // đọc màu trong composition nên LiveBadge chạy lại mỗi khung hình.
    Text(
        text = text,
        color = Color.White,
        modifier = Modifier
            .drawBehind {
                // Màu chỉ được đọc ở giai đoạn vẽ
                drawRoundRect(color = bgColor, cornerRadius = CornerRadius(8.dp.toPx()))
            }
            .padding(horizontal = 12.dp, vertical = 4.dp)
    )
}

Kết quả: Nhãn "TRỰC TIẾP" (khi gọi LiveBadge("TRỰC TIẾP")) có nền đỏ chuyển qua lại giữa đậm và nhạt. Với background, Layout Inspector cho thấy số lần recompose tăng liên tục; với drawBehind, số lần recompose đứng yên vì chỉ giai đoạn vẽ chạy lại.

Chú ý

  • Đừng tối ưu khi chưa đo. Code dễ đọc quan trọng hơn vài micro giây; chỉ sửa chỗ công cụ chỉ ra là chậm.
  • Đếm số lần recompose bằng Layout Inspector trên bản debug là được, nhưng đo thời gian (khởi động, độ giật) phải làm trên bản release, tốt nhất trên thiết bị thật.
  • @Immutable và @Stable là lời hứa với trình biên dịch. Đánh dấu một class mà thực tế vẫn bị sửa bên trong sẽ khiến UI không cập nhật như mong đợi.
  • derivedStateOf chỉ có ích khi kết quả đổi ít hơn state đầu vào. Nếu kết quả đổi theo từng lần input đổi (vd ghép họ và tên), chỉ cần remember(key) hoặc tính trực tiếp.
  • Với giá trị đổi liên tục, có thể truyền lambda (() -> Float) cho composable con thay vì truyền giá trị, để con tự đọc ở giai đoạn layout hoặc vẽ.
  • Luôn đặt key ổn định cho item trong lazy list có thể thêm, xóa hoặc đổi thứ tự.
Cảnh báo: Đừng tự kết luận "Compose chậm" sau khi chạy bản debug trên emulator. Hãy so sánh trên bản release có R8 và Baseline Profile trước khi quyết định viết lại bất cứ thứ gì.
