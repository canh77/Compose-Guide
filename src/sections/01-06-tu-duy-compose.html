Tư duy trong Compose

Compose không chỉ là một cú pháp mới mà là một cách nghĩ khác về giao diện: bạn mô tả giao diện cho từng trạng thái, còn Compose quyết định khi nào và phần nào cần vẽ lại. Hiểu đúng điều này giúp tránh phần lớn lỗi khó hiểu mà người mới hay gặp.

Định nghĩa

Trong mô hình khai báo, giao diện là một hàm của trạng thái: UI = f(state). Hàm composable nhận dữ liệu và mô tả giao diện tương ứng; nó không giữ tham chiếu tới phần tử nào để sửa sau này. Muốn giao diện thay đổi, bạn thay đổi dữ liệu, rồi Compose gọi lại hàm với dữ liệu mới.

Việc gọi lại các hàm composable khi dữ liệu đầu vào thay đổi gọi là recomposition (tái tổ hợp). Compose theo dõi hàm nào đọc state nào. Khi một state thay đổi, chỉ những hàm (chính xác hơn là những phạm vi code) có đọc state đó mới được lên lịch chạy lại; các composable con có tham số không đổi sẽ được bỏ qua (skip). Cơ chế này gọi là smart recomposition, giúp cập nhật nhanh dù bạn "vẽ lại" về mặt khái niệm.

So với View: ở đó bạn giữ đối tượng TextView và gọi setText. Ở Compose không có đối tượng nào để giữ — chỉ có hàm và state. Đây là lý do code Compose ngắn hơn nhưng đòi hỏi bạn tuân thủ vài quy tắc nghiêm ngặt về cách viết hàm.

Quy tắc rút ra

  1. Idempotent: cùng đầu vào thì cho cùng giao diện, dù hàm chạy một lần hay một trăm lần.
  2. Không side effect trong thân hàm: không ghi biến bên ngoài, không ghi SharedPreferences, không gọi mạng, không ghi log thống kê. Những việc này đặt trong lambda sự kiện (như onClick) hoặc trong các API như LaunchedEffect, SideEffect — xem Side effects.
  3. Nhanh: tính toán tốn kém thì đưa vào ViewModel, hoặc tối thiểu bọc trong remember để không lặp lại mỗi lần recomposition.
  4. Mọi dữ liệu thay đổi phải là state Compose theo dõi được (mutableStateOf, StateFlow được collect…). Biến Kotlin thường thay đổi sẽ không kích hoạt recomposition — xem State và remember.

Ba giai đoạn của một khung hình

Mỗi lần cập nhật, Compose đi qua ba giai đoạn: Composition (chạy hàm composable để biết hiển thị cái gì), Layout (đo và đặt ở đâu), Drawing (vẽ ra màn hình). Đọc state ở giai đoạn càng muộn thì càng ít việc phải làm lại. Chi tiết ở Vòng đời và các giai đoạn.

Ví dụ

Ví dụ 1: Bộ đếm viết đúng cách

@Composable
fun LikeButton(modifier: Modifier = Modifier) {
    var likes by remember { mutableIntStateOf(0) }

    Button(onClick = { likes++ }, modifier = modifier) {
        Text("Thích ($likes)")
    }
}

Kết quả: Nút hiện "Thích (0)". Mỗi lần bấm, likes tăng trong lambda sự kiện (không phải trong thân hàm), state thay đổi, phần đọc likes được chạy lại và nút hiện "Thích (1)", "Thích (2)"…

Ví dụ 2: Chỉ phần đọc state mới chạy lại

@Composable
fun WeatherPanel() {
    var city by remember { mutableStateOf("Hà Nội") }
    var temperature by remember { mutableIntStateOf(28) }

    Column(modifier = Modifier.padding(16.dp)) {
        CityHeader(city = city)              // chỉ chạy lại khi city đổi
        TemperatureText(value = temperature) // chỉ chạy lại khi temperature đổi
        Row {
            Button(onClick = { temperature++ }) { Text("+1°C") }
            Button(onClick = { city = "Huế" }) { Text("Đổi sang Huế") }
        }
    }
}

@Composable
fun CityHeader(city: String) {
    Text(text = city, style = MaterialTheme.typography.headlineSmall)
}

@Composable
fun TemperatureText(value: Int) {
    Text(text = "$value°C", style = MaterialTheme.typography.displayMedium)
}

Kết quả: Bấm "+1°C" thì số nhiệt độ tăng. Phía sau, WeatherPanel và TemperatureText chạy lại, còn CityHeader bị bỏ qua vì city vẫn là "Hà Nội". Bấm "Đổi sang Huế" thì điều ngược lại xảy ra.

Ví dụ 3: Lỗi side effect trong thân hàm và cách sửa

SAI: ghi vào danh sách bên ngoài trong lúc compose

data class Note(val id: Long, val title: String)

val viewedNoteIds = mutableListOf<Long>() // nằm ngoài composable

@Composable
fun NoteList(notes: List<Note>) {
    Column {
        notes.forEach { note ->
            viewedNoteIds.add(note.id) // SAI: side effect, chạy lại mỗi lần recomposition
            Text(note.title)
        }
        Text("Đã xem ${viewedNoteIds.size} ghi chú") // con số sai và cứ tăng dần
    }
}

Mỗi lần NoteList chạy lại (do danh sách đổi, do theme đổi, do cha recompose…), các id lại bị thêm vào lần nữa. Con số hiển thị không phản ánh dữ liệu thật, và vì viewedNoteIds không phải state nên giao diện cũng không cập nhật đúng lúc.

ĐÚNG: hiển thị tính từ tham số, side effect đưa vào LaunchedEffect

@Composable
fun NoteList(
    notes: List<Note>,
    onNotesShown: (List<Long>) -> Unit,
    modifier: Modifier = Modifier
) {
    // Chỉ chạy khi danh sách notes thực sự thay đổi, không chạy theo mỗi recomposition
    LaunchedEffect(notes) {
        onNotesShown(notes.map { it.id })
    }

    Column(modifier = modifier) {
        notes.forEach { note ->
            Text(note.title)
        }
        Text("Đang hiển thị ${notes.size} ghi chú")
    }
}

Kết quả: Dòng cuối luôn hiển thị đúng số ghi chú hiện có. Việc ghi nhận "đã xem" được báo lên trên (ví dụ cho ViewModel xử lý) đúng một lần cho mỗi danh sách mới, dù hàm có recomposition bao nhiêu lần.

Chú ý

  • Thay đổi state ngay trong thân hàm (ví dụ viết count++ trực tiếp, không nằm trong onClick) sẽ kích hoạt recomposition, recomposition lại chạy count++… tạo vòng lặp vô tận. Chỉ thay đổi state trong sự kiện hoặc effect.
  • Biến khai báo bằng var x = 0 trong thân composable bị khởi tạo lại mỗi lần recomposition; dùng remember { mutableStateOf(…) } để giữ giá trị.
  • Đừng đếm số lần recomposition để làm logic, và đừng giả định thứ tự chạy giữa các composable anh em.
  • Truyền dữ liệu bất biến (data class val, List chỉ đọc) để Compose so sánh được và bỏ qua những phần không đổi. Từ Kotlin 2.0.20, chế độ strong skipping được bật mặc định nên cả composable có tham số không ổn định cũng có thể được bỏ qua — xem Hiệu năng.
  • Muốn xem thực tế hàm nào recomposition bao nhiêu lần, dùng Layout Inspector của Android Studio (hiện số lần recomposition và số lần bị bỏ qua).
Cảnh báo: Code trong thân composable chạy trên luồng giao diện. Gọi mạng, đọc database hay sắp xếp danh sách lớn ở đây sẽ làm giật hoặc treo app — luôn đưa vào ViewModel hoặc coroutine.
